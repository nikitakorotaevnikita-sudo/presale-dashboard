# ИИ-чат аналитики пресейла — дизайн

**Дата:** 2026-09-08
**Проект:** presale-dashboard
**Автор постановки:** Никита Коротаев (руководитель пресейла ОГВ)

## 1. Задача

Добавить в дашборд ИИ-чат, который по данным пресейла помогает руководителю находить узкие места процесса, проводить анализ и получать рекомендации. Ключевое требование — **ответы без галлюцинаций**: числа должны быть точными.

**Сценарии:**
- Руководитель советуется в чате про узкие места, сложности из-за конкретного исполнителя/команды.
- Одной кнопкой получает структурный отчёт «Анализ узких мест» (проблемы + числа-обоснование + рекомендации).
- Настраивает доступ к LLM в бэкофисе (по умолчанию — локальный провайдер).

## 2. Ключевое архитектурное решение (анти-галлюцинации)

Подход **A — грудинг через «сводку данных»**. Все числа считаются детерминированно в коде (переиспользуя `metrics.py`) и вкладываются в контекст LLM как блок ДАННЫЕ. LLM **не считает арифметику** — только интерпретирует готовые числа и формулирует рекомендации. Данные пресейла небольшие, поэтому полная сводка помещается в контекст и покрывает почти любой вопрос.

Отклонённые альтернативы:
- **B (tool-calling)** — гибче, но надёжность tool-calling у локального Qwen непредсказуема (в экосистеме уже наблюдались пропуски вызовов и кракозябры в кириллических аргументах).
- **C (гибрид)** — A + инструменты детализации. Заложено как возможное развитие, но не в v1.

Архитектура модулей позволяет добавить инструменты (перейти к C) позже без переписывания.

## 3. Стек и ограничения

- Python 3.10+, FastAPI, Uvicorn (как в проекте).
- Frontend: Vanilla JS, plain HTML/CSS — без фреймворков.
- LLM: OpenAI-совместимый SDK (`openai>=1.x`), работает с локальным провайдером.
- Данные и настройки: SQLite.
- Тесты: pytest + Playwright, покрытие ≥70%, TDD.
- Общение с пользователем — на русском.
- Секреты (токен LLM) — не в git, не в логах, в API только замаскированы.

## 5. Сводка данных (`analytics_brief.py`)

Строит один компактный текстовый блок из точных чисел. Декабрь исключён (текущее правило `metrics.EXCLUDED_MONTHS`).

**Содержимое:**

1. **Шапка:** период с данными, всего запросов, дата/имя загрузки. Строка-предупреждение: «Все числа рассчитаны системой; не пересчитывай их».
2. **Матрицы показателей** (месяц × разрез, компактно):
   - Поступило, Проработано — по услугам и по командам + итоги (`build_matrix`, `month_totals`).
   - Ср. трудоёмкость (ч), Ср. длительность (раб.дн), Ср. на контроле (раб.дн) — по услугам и по командам.
3. **Производные индикаторы узких мест** (считаются в коде):
   - Backlog по месяцам = Поступило − Проработано.
   - Пропускная способность = Проработано / Поступило.
   - Рейтинг команд по ср. длительности, по ср. «на контроле», по ср. трудоёмкости.
   - Рейтинг услуг по трудоёмкости/длительности.
   - Выбросы: max по каждому индикатору (команда/услуга).
4. **Машинный JSON-срез** тех же индикаторов — детерминированный каркас для отчёта.

**Формат:** короткие markdown-таблицы / строки `ключ: значение`. Для текущих объёмов отдаётся целиком; при росте — топ-N (не требуется в v1).

Функции: `build_brief(events) -> str` (текст для LLM), `bottleneck_indicators(events) -> dict` (JSON-срез).

## 6. Промпты (`chat_service.py`)

**Системный промпт** (русский): роль — аналитик процесса пресейла ОГВ. Правила:
1. Использовать только числа из блока ДАННЫЕ; не пересчитывать и не выдумывать.
2. В выводах цитировать конкретные числа (команда/услуга/месяц/значение).
3. Если данных нет — прямо сказать «В данных этого нет».
4. Рекомендации опирать на конкретные индикаторы из ДАННЫХ.
5. Отвечать по-русски, кратко и по делу.

**Структура запроса:** `system` (правила) → блок ДАННЫЕ (сводка, вкладывается один раз, стабилен между ходами) → история диалога → новый вопрос. Температура ~0.2.

**`analyze_bottlenecks()`** — фикс-промпт поверх той же сводки: «Определи 3–5 проблемных зон. Для каждой: (а) в чём проблема, (б) числа-обоснование из ДАННЫХ, (в) рекомендация. Отсортируй по критичности».

**Подсказки** (`/api/chat/suggestions`) — статический список, например: «Какая команда дольше всех держит запросы?», «Где копится backlog?», «У каких услуг самая высокая трудоёмкость?», «Кто медленнее переводит из инициализации в работу?».

## 7. API (в `main.py`)

- `GET /api/settings/llm` — текущий конфиг, токен замаскирован (`••••386d`).
- `POST /api/settings/llm` — сохранить (провайдер, base_url, model, token). Пустой токен не затирает прежний. Валидация URL/модели.
- `POST /api/llm/test` — пробный вызов, возвращает ok/ошибку с диагностикой.
- `POST /api/chat` — стриминг ответа; тело: история сообщений. Сводка добавляется на бэкенде.
- `POST /api/analyze` — отчёт узких мест (стриминг или единый ответ).
- `GET /api/chat/suggestions` — список подсказок.

Стриминг — chunked/SSE, фронт рендерит по мере поступления.

## 8. Конфигурация LLM

Хранится в SQLite (`app_settings`), редактируется в бэкофисе в рантайме. Поля: `provider` (default `local`), `base_url`, `model`, `token`.

**Значение по умолчанию (сидинг при первом старте):**
- base_url: `https://llm.ario.directum360.ru/v1`
- model: `Qwen/Qwen3-8-27B` (уточнить точное имя модели у провайдера при реализации)
- token: из переменной окружения `LLM_TOKEN`, если задана; иначе пусто (вводится в бэкофисе).

Токен реального провайдера **в git не попадает**: `.env.example` содержит плейсхолдер, реальное значение — в БД (введено через бэкофис) или в локальном `.env`.

## 9. Обработка ошибок

- LLM недоступен/таймаут/ошибка авторизации → понятное русское сообщение в чате, приложение не падает. Таймаут запроса к LLM 60–120 с.
- Ошибка в середине стрима → стрим завершается с пометкой, показанный текст сохраняется.
- Нет данных в БД → чат и отчёт отвечают «Сначала загрузите данные», без вызова LLM.
- Токен не логируется и не отдаётся целиком через API.

## 10. Тестирование

Реальный LLM в тестах не вызывается — клиент мокается.

- **Unit `analytics_brief`** (главный): на синтетических событиях — верные числа и индикаторы (backlog, рейтинги команд, исключение декабря).
- **Unit `settings_store`**: roundtrip, сидинг дефолта, маскирование токена, «пустой токен не затирает прежний».
- **Unit `chat_service`**: в промпте есть блок ДАННЫЕ и правила; история передаётся; `analyze_bottlenecks` использует фикс-промпт (LLM замокан).
- **Unit `llm_service`**: `test_connection`, обработка ошибок (таймаут/авторизация) на моке.
- **API-тесты**: маскирование в `/api/settings/llm`; `/api/llm/test` (мок); `/api/chat` и `/api/analyze` со стрим-ответом мок-клиента; поведение «нет данных».
- **E2E (Playwright)**: бэкофис — сохранение настроек и маска; ИИ-аналитик — рендер, отправка вопроса, появление ответа (LLM мокается на бэкенде). Скриншоты → `tmp/screenshots/`.
- Покрытие ≥70%.

## 11. Вне объёма (YAGNI)

- Tool-calling / автономная выборка срезов LLM (возможное развитие — подход C).
- Персистентная история чатов между сессиями (v1 — история в рамках сессии/вкладки).
- Авторизация/роли (внутренний инструмент в локальной сети, как и весь дашборд).
- Дообучение/оценка качества модели.

## 12. Открытые вопросы к реализации

- Точное имя модели у провайдера (`Qwen/Qwen3-8-27B` — уточнить через `/v1/models` или у провайдера).
- Формат стриминга (SSE vs chunked) — выбрать на этапе реализации по совместимости с Vanilla JS `fetch`.
