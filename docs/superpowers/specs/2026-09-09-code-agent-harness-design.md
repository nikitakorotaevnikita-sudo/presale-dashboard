# Code-agent (харнесс анализа кодом) — дизайн

**Дата:** 2026-09-09
**Проект:** presale-dashboard
**Автор постановки:** Никита Коротаев
**Статус:** Phase 2 (расширение ИИ-аналитика; базовый чат — подход A — уже в проде)

## 1. Задача

Дать ИИ-аналитику возможность отвечать на **нестандартные** вопросы, которых нет в заранее посчитанной сводке (подход A): произвольные срезы, кросс-расчёты, нетиповые агрегаты. Для этого LLM **пишет Python-код**, который исполняется над данными в песочнице, и ответ формируется по **реально вычисленному** результату.

Ключевое противоречие: исполнение сгенерированного кода мощно и гибко, но угрожает (а) безопасности (произвольное исполнение) и (б) корректности (тихо неверный код → уверенно неверные числа). Дизайн решает это песочницей и гардрейлами; числа берутся из фактического прогона, а не из «воображения» модели.

## 2. Решения по объёму (согласованы)

- **Отдельный opt-in режим.** По умолчанию остаётся надёжный чат (подход A). Code-agent включается пользователем явно тумблером «Глубокий анализ (код)».
- **Песочница — отдельный Python-подпроцесс** (не Docker, не in-process).
- **Модель — та же локальная Qwen3.8-27B**; надёжность кодогенерации подпирается агентной петлёй самокоррекции (≤2 повтора по трейсбеку).
- Данные в песочницу — pandas DataFrame (копия, декабрь исключён); секреты (токен, путь к БД) в подпроцесс не передаются.

## 3. Стек и ограничения

- Python 3.10+, FastAPI, Uvicorn; новая зависимость: **pandas** (+ numpy как транзитивная).
- Frontend: Vanilla JS, без фреймворков; UI/текст — на русском.
- Реальный LLM в тестах не вызывается (мок / `LLM_FAKE`).
- TDD; покрытие ≥70%.
- Секреты не в git и не в логах; в подпроцесс не попадают.
- Общение с пользователем — на русском.

## 4. Компоненты

```
src/
├── agent_sandbox.py   # раннер подпроцесса: исполнение кода в изоляции
├── code_agent.py      # агентная петля: кодоген -> прогон -> (повтор) -> ответ
└── main.py            # + эндпоинт POST /api/agent
static/                # + тумблер «Глубокий анализ (код)» и показ кода в чате
```

Каждый модуль — одна ответственность, тестируется изолированно (LLM мокается).

## 5. Песочница (`agent_sandbox.py`)

Интерфейс: `run_code(code: str, events: list[StatusEvent], timeout: float = 15) -> dict` →
`{"ok": bool, "result": <json|str>, "explanation": str, "error": str|None}`.

**Механика:**
1. **Отдельный процесс.** Раннер пишет во временную папку: (а) сериализованный снимок данных (JSON/parquet), (б) сгенерированный код, (в) скрипт-обёртку. Запускает `python` (наш venv) как подпроцесс с `cwd` = временная папка. Забирает `stdout` (JSON) и `stderr` (трейсбек). Папка удаляется после.
2. **Namespace кода.** Доступны только: `df` — pandas DataFrame событий (копия, декабрь исключён), и модули из **белого списка импортов**: `pandas, numpy, math, statistics, json, datetime, collections`. Подменённый `__import__` бросает `ImportError` на всё остальное (`os, sys, subprocess, socket, shutil, requests, pathlib` и т.п.).
3. **Отключённые builtins.** Из namespace убраны `open, eval, exec, compile, input, __import__`(кроме обёртки), `globals`, `locals`. Писать в ФС и открывать сокеты нечем.
4. **Сеть.** В преамбуле обёртки глушится `socket` (методы `connect` бросают). В проде (Docker/Linux) дополнительно — запуск без сетевого доступа.
5. **Лимиты.** Тайм-аут (`communicate(timeout=15)` + kill зависшего). На Linux (Docker-прод) — `resource.setrlimit(RLIMIT_AS, RLIMIT_CPU)` в преамбуле ребёнка. На Windows-dev достаточно тайм-аута. Кап на размер `stdout`.
6. **Секреты.** Подпроцесс получает только снимок данных — ни токена, ни пути к БД, ни конфигурации LLM.
7. **Контракт кода.** Сгенерированный код обязан присвоить `result` (JSON-сериализуемый) и, опционально, `explanation` (str). Обёртка печатает `json.dumps({"result": result, "explanation": explanation})`. Не-сериализуемый `result` приводится к `str`.

## 6. Агентная петля (`code_agent.py`)

Интерфейс (стриминг): `stream_agent(config, events, history, upload=None)` — генератор чанков для UI.

**Промпт кодогенерации** (русский, строгий):
- Роль: пишешь Python (pandas) для анализа процесса пресейла.
- Дан DataFrame `df` со **словарём данных**: перечень колонок (из полей `StatusEvent`) и правила метрик — дедуп по `ИД запроса`; «поступило» = статус «Инициализация»; «проработано»/средние = статус «Принято»; длительность из колонки «Длительность проработки запроса»; декабрь уже исключён.
- Требования: только чтение `df`; присвоить `result` (число/таблица/словарь) и `explanation`; без сети/ФС/импортов вне белого списка.

**Петля:**
1. LLM → код. 2. `agent_sandbox.run_code`. 3. Если `ok` — LLM формирует финальный ответ, **цитируя `result`** (или отдаём `explanation` напрямую). 4. Если ошибка — трейсбек возвращается модели, повтор (макс. 2). 5. После исчерпания повторов — сообщение об ошибке + подсказка вернуться к надёжному чату.

**Стриминг в UI:** этапы — «пишу код» → сам код → «исполняю» → результат/ответ.

## 7. API (`main.py`)

- `POST /api/agent` — тело `{messages:[{role,content}]}`, `StreamingResponse` (text/plain, UTF-8). Грузит события (декабрь-исключение — как в чате), гоняет `code_agent`. Поведение «нет данных» → 400 «Сначала загрузите данные» (как у `/api/chat`). Ошибки LLM/песочницы ловятся и отдаются понятным русским текстом внутри стрима (не 500).
- Тестовый режим `LLM_FAKE=1` → детерминированный код/ответ (для E2E), ветка после проверки данных.

## 8. Фронтенд

- Во вкладке «ИИ-аналитик» — тумблер **«Глубокий анализ (код)»**. Выключен → вопрос идёт на `/api/chat` (подход A). Включён → на `/api/agent`.
- Ответ code-agent: **сворачиваемый блок со сгенерированным кодом** (прозрачность) + текст ответа (Markdown-рендер уже есть). Показ кода — моноширинный, экранированный.
- Тумблер и маршрутизация — минимальная правка `app.js`; существующий чат не ломается.

## 9. Корректность и её границы

- Числа — из **реального прогона** кода над реальными данными (не галлюцинация).
- Гардрейлы корректности: точный словарь данных с правилами метрик в промпте; показ кода пользователю (проверяемость); самокоррекция по ошибкам исполнения.
- **Остаточный риск:** логически неверный, но исполнимый код может дать точное-но-неправильное число. Смягчение: прозрачность (код виден), opt-in (осознанное использование), надёжный чат остаётся дефолтом.
- **Будущее усиление (v2, вне объёма):** переиспользование проверенных `metrics`-хелперов внутри песочницы вместо «сырого» pandas.

## 10. Тестирование

Реальный LLM не вызывается (мок/`LLM_FAKE`).

- **`agent_sandbox`** (главный по безопасности): исполняет безопасный код и возвращает `result`; **блокирует** `import os`, `open(...)`, `import socket` (ожидается ошибка/пустой результат, не побочный эффект); соблюдает тайм-аут (зависший код убивается); не-сериализуемый `result` приводится к строке; секреты недоступны.
- **`code_agent`**: петля на моке `llm_service` — код→прогон→`result`; ошибка исполнения→повтор→успех; исчерпание повторов→сообщение об ошибке.
- **API `/api/agent`**: с `LLM_FAKE` — стрим с кодом и ответом; «нет данных» → 400.
- **E2E (опц.)**: тумблер переключает режим; ответ code-agent с блоком кода появляется (LLM замокан).
- Покрытие ≥70%.

## 11. Вне объёма (YAGNI)

- Docker-песочница (усиление изоляции) — при необходимости позже.
- Отдельная code-модель — пока та же локальная.
- Генерация графиков кодом (matplotlib) — возможное расширение; в v1 результат текст/таблица/число.
- Переиспользование `metrics`-хелперов в песочнице — v2.
- Память/персистентность истории code-agent между сессиями.

## 12. Открытые вопросы к реализации

- Формат снимка данных в подпроцесс: JSON vs parquet (parquet быстрее/типобезопаснее, но +зависимость `pyarrow`). Решить на реализации; по умолчанию — JSON (без доп-зависимостей).
- Windows-лимиты ресурсов: `setrlimit` частично недоступен — полагаемся на тайм-аут; прод под Linux/Docker получает полные лимиты.
